# 架構與流程

## 1. 整體流程

```
                    ┌──────────── LLM（DeepSeek／llama.cpp）────────────┐
小說章節 ─────────► │ ① 改編規劃 → ② 漫畫劇本 → ③ 分鏡 JSON            │
視覺聖經（角色、地點）│   章→頁、節拍    人看、人改     機器讀、只寫 id 與比例 │
                    └───────────────────────────────┬──────────────────┘
                                                    ▼
                         ④ 編譯（t2c/compile.py，純程式，不用 LLM）
                            角色 id → 聖經的 look_en（逐字）
                            比例座標 → MOSS bbox（abs_centralized、yxyx）
                            格子形狀 → 生圖尺寸（約 1 MP、16 的倍數）
                                                    ▼
                         ⑤ 出圖（ComfyUI＋MOSS-Image）每格 N 個 seed
                                                    ▼
                         ⑥ 挑圖 → ⑦ 組版（t2c/compose.py）→ ⑧ 嵌字（t2c/letter.py）→ ⑨ PDF／CBZ
```

分工的原則：**LLM 只做需要理解故事的事；能用規則做的一律交給程式。** LLM 寫錯外觀、算錯座標的機率很高，而這兩件事程式可以百分之百做對。

## 2. 為什麼這樣設計：MOSS-Image 的特性

以下是 S0 時查到的資料（2026-11），S1 實測（`docs/qa/S1_出圖實測.md`）的結果已在「S1 實測」欄補上。

| 特性 | 對設計的影響 |
|---|---|
| 5B 單流 DiT，文字編碼器 Qwen3.5 9B，FLUX.2 VAE；ComfyUI 0.42.0 以上內建支援 | workflow 用內建節點即可，不需要自訂節點 |
| **沒有圖片輸入**：ComfyUI 範本的 `ref_image` 只送給 prompt 改寫用的 LLM，擴散模型本身看不到 | 不能用參考圖鎖角色。角色一致性只能靠「每次逐字相同的外觀描述」，進階再靠角色 LoRA（用 Base 訓練、凍結文字編碼器） |
| prompt 可以是 layout JSON：`summary`＋`items`（每項有 `label`、`caption`、`bbox`，文字項另有 `text`） | 分鏡天生就能寫成資料；每格的人物、物件位置可以指定 |
| bbox 是像素、原點在畫布中心、順序 `[y_min, x_min, y_max, x_max]` | 太容易寫錯，所以 LLM 只寫比例，換算集中在 `layout.to_moss_bbox()` |
| bbox 是建議不是裁切：文字大多留在框內，角色常常超出框 | 用來決定大致構圖就好，不要期待精準。**S1 實測：兩人同格時左右位置會對調（k5 只對 1/3）**，編譯時在角色 caption 前加左右位置句（`side_of_frame`），改後 3/3 |
| 角色寫在全域描述裡會跑進不該出現的格子（社群實測） | 一格一張圖；summary 只寫這一格；寫明人數與「每人只出現一次」 |
| 繁中字渲染準確度高但不是 100%（社群實測 147/147、另一輪 36 張裡 2 個錯字），常要多跑幾個 seed | 對話不交給 MOSS 畫，改成嵌字；狀聲詞可選（`sfx_mode`）。S3 的嵌字在組版後的整頁上做：對話框依分鏡的 `anchor` 自動找位置、避開從角色框推估的臉，人再到介面拖曳微調（`letters/`） |
| prompt 裡寫大寫的「NO TEXT」會被畫成標題（社群實測） | 用小寫敘述句「The artwork has no speech bubbles, captions or lettering.」**S1 實測：15 張沒有多出任何文字，沒有副作用**。另加「The image has no border or frame.」，邊框 3/15 → 0/15 |
| 建議輸出 1–2 MP，寬高為 16 的倍數，可到約 4 MP | 每格約 1 MP；組版時再縮放、裁切 |
| 官方範本：25 步、CFG 2.5、`er_sde`；Base 官方 50 步、CFG 3、`euler` | 預設照範本（`final`）。S1 實測：每張約 13–14 秒，一頁 5 格×3 seed 約 3.3 分鐘 |
| 社群 4-step LoRA（`akhaliq/MOSS-Image-SFT-4-steps`）：4 步、CFG 1；但在 ComfyUI 的 int8 權重上用內建 LoRA 載入器會**默默只套用一部分**，要看 log 裡 `lora key not loaded` 的行數 | **S1 實測**：4 步＋LoRA（`draft` 預設）每張約 4.1 秒，快約 3.3 倍，VRAM 多 0.1 GiB；線條較乾淨、網點與墨線的漫畫感較少；探測載入時沒看到 `lora key not loaded`（只是沒看到，不是證明全部套用）。CFG 1 時負向提示詞不起作用，可以把負向換成 `ConditioningZeroOut` 省時間（`t2c/comfy.py` 已支援） |

參考資料：

- ComfyUI 官方教學：https://docs.comfy.org/tutorials/image/moss-image/moss-image.md
- 模型權重：https://huggingface.co/Comfy-Org/MOSS-Image
- 繁中文字與漫畫卡實測：https://ai-muninn.com/en/blog/moss-image-traditional-chinese-comic-cards
- 小說轉漫畫 skill 分工參考：lhfer/codex-novel-to-comic-studio（GitHub；用前先確認授權）

## 3. 本機資源（RTX 5070 Ti 16GB、64GB RAM）

| 項目 | 大小 | 說明 |
|---|---|---|
| `moss_image_sft_int8_convrot.safetensors` | 約 5.4 GB | 主模型 |
| `qwen3.5_9b_w4a8_gptq.safetensors` | 約 7.3 GB | 文字編碼器（GPU 用這個。S1 實測 W4A8 放 CPU：新提示詞 175 秒 vs GPU 14.5 秒，VRAM 沒省；int8＋CPU 未測） |
| `flux2-vae_small.safetensors` | 約 0.25 GB | VAE |

- 主模型＋W4A8 文字編碼器大約 13 GB，16 GB 的卡可以全部放 GPU。S1 實測取樣時整機約用 6.8 GiB（`--disable-smart-memory`，編碼器用完即卸載）。
- **llama.cpp 與 ComfyUI 不要同時佔 GPU**：文字端（①–③）跑完再出圖。用 DeepSeek 時沒有這個問題。S7 的整章批次要做排程：先跑完整章的 LLM 階段，再釋放、再出圖。

## 4. 程式結構

| 層 | 位置 | 可以依賴 |
|---|---|---|
| 核心 | `t2c/` | 標準函式庫、PyYAML、Pillow |
| 命令列 | `tools/*.py` | 核心 |
| 介面後端 | `app.py` | 核心、fekit、FastAPI |
| 介面前端 | `web/static/` | fekit（`window.FE`） |

核心不依賴網頁框架，整合時有兩種做法（I1、I3 決定）：

1. **整包複製**：像 fekit 一樣把 `t2c/` 放進對方的 `vendor/`，用同步工具更新。
2. **資料交換**：對方匯出成 t2c 的漫畫專案資料夾（`project.yaml`＋聖經＋劇本），由本工具處理。

## 5. 名詞

| 名詞 | 意思 |
|---|---|
| 頁（page） | 一張 B5 比例的漫畫頁 |
| 格（panel） | 頁裡的一個框，對應一張生成圖 |
| slot | 格子在模板裡的編號，也是閱讀順序（右翻：右上開始） |
| 候選（candidate） | 同一格用不同 seed 生成的圖 |
| 視覺聖經（bible） | 角色、地點的固定外觀描述 |
| 嵌字（lettering） | 把對話框、台詞、狀聲詞疊到圖上 |
